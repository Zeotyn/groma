# groma-agents

One source of instructions: `AGENTS.md`. Every other agent file only points to it.

**Writes are additive.** Create a file only when its path does not exist. For an existing file, put the suggested line into the findings report.

The findings report is this run's `<project>/docs/_groma/findings-<YYYY-MM-DD>.md`. When none exists (groma-agents run on its own), create it with the title `# groma findings, <YYYY-MM-DD>` and put every snippet under `## Snippets for existing files`.

## Steps

1. **AGENTS.md.** If `<project>/AGENTS.md` is absent, fill [templates/AGENTS.md](templates/AGENTS.md):
   - commands: read them from the environment (`package.json` scripts, `Makefile`, `pyproject.toml`, `pom.xml`, `go.mod`, CI workflow); exact commands only, `Not yet documented.` when none exist.
   - methodology, workflow and skills: from `.groma/config.yaml`; `methodology_hint` is one sentence on where changes live (for example "Changes live in openspec/changes/; use /opsx:propose").
   - change naming: the rule text from [references/naming-rule.md](references/naming-rule.md) (a copy of groma-methodology's), with the config's types.
   - `status_script`: the path of `../groma-methodology/scripts/status.sh` as the project's agents will reach it (relative to the project when the skill is installed project-locally, else the installed path). groma-methodology missing: drop the "Session start" and "Session end" sections and tell the user to add it (`npx skills add Zeotyn/groma --skill groma-methodology`) for the status and next-action reminders.
   - `next_script`: the path of `../groma-methodology/scripts/next.sh`, resolved like `status_script`.
   - `review_mode`: `review.mode` from the config (default `autonomous`). groma-loop not installed: drop that bullet.
   - `docs_impact_script`: the path of `../groma-lay-out/scripts/docs-impact.sh`, resolved like `status_script`. `docs.gate: off`: drop the "Living docs" bullet. groma-lay-out missing: drop it too and tell the user to add it (`npx skills add Zeotyn/groma --skill groma-lay-out`) for the docs check.
   - `code_style_doc`: the file that fills the code-style slot (`docs/code-style.md`, or the style guide the docs index links for it). `style_checks`: the check commands from that doc's "Enforced by tools" table, one per line; no tool: `None configured.`. Do not copy conventions into AGENTS.md; the pointer is enough.
   - "Git workflow" section, from the `git` keys of the config (missing keys: `integrate: rebase`, `branch_per_change: true`, `commits: conventional`, `push: ask`). `main_branch`: the "Main branch" rule of [references/git-strategies.md](references/git-strategies.md) (the remote's default branch, else `main`, else `master`, else `main`). `git_integrate` and `git_abort`: the Commands and On conflict cells of the configured strategy's row in that table, with `<main>` resolved and `<branch>` and `<message file>` kept. `commits_rule`: `conventional` → "Conventional Commits, `<type>(<change-id>): <summary>`"; `free` → "free subjects". `push_rule`: `ask` → "push `<main>` only when the user agreed"; `auto` → "push `<main>` after every integration"; `never` → "never push, the user pushes". `branch_per_change: false`: replace the branch bullet with "Work on `<main>` directly; groma-loop creates no branches." Not a git repository: drop the section.
   Keep it within 80 lines. Done when no `{{` remains.

2. **Pointer files.** For each agent in `agents`, create the file from [templates/](templates/README.md) when absent:

   | Agent | File | Template |
   |---|---|---|
   | claude | `CLAUDE.md` | `templates/CLAUDE.md` |
   | gemini | `GEMINI.md` | `templates/GEMINI.md` |
   | copilot | `.github/copilot-instructions.md` | `templates/copilot-instructions.md` |
   | cursor | `.cursor/rules/groma.mdc` | `templates/groma.mdc` |
   | codex | none, reads AGENTS.md | - |

3. **Existing files.** For each existing agent file that does not mention `AGENTS.md`, add a snippet to the findings report: for `CLAUDE.md`/`GEMINI.md` the line `@AGENTS.md`, for Copilot and Cursor the sentence from the template. Existing `AGENTS.md` without a link to `docs/README.md`: suggest the "Read first" section. Existing `AGENTS.md` without a "Git workflow" section (in a git repository): put the section of the template, rendered as in step 1, into the findings report as a snippet; an existing file is never edited, not even one groma wrote in an earlier run.

4. **Session hook (Claude Code, optional).** Steps 4 and 5 run groma-methodology's scripts; when that skill is missing, skip both and tell the user to add it (`npx skills add Zeotyn/groma --skill groma-methodology`). When `claude` is in `agents`, ask once: "Run the groma status reminder automatically at every Claude Code session start?" On yes, fill [templates/claude-session-hook.json](templates/claude-session-hook.json) with the absolute path of `status.sh`; it goes to `<project>/.claude/settings.local.json` (machine-specific, not committed), written once after step 5 so that both hooks land in the same new file. If that file already exists, show the `hooks` block and add it only after the user approves that edit; otherwise put it into the findings report as a snippet. On no, change nothing; the AGENTS.md line remains the reminder.

5. **Next action (optional).** Hook support per agent is the `hook` entry in [agents.yaml](agents.yaml). When `claude` is in `agents`, ask once: "Show groma's next action in Claude Code (hooks) and in your status line? (yes = both, or name one)" Never offer this again in a later run unless the user asks. The groma plugin is installed when `claude` is in `agents_via_plugin` of `.groma/config.yaml` or this skill itself runs from a Claude Code plugin folder; do not look outside the project to find out.
   - **Yes, hooks, plugin installed:** the plugin ships the hooks (SessionStart gives the next action to the agent, Stop shows it to the user after an answer), so write no settings file and leave `next.hook` in `.groma/config.yaml` as it is. Put into the findings report and the summary, in the user's language: the command `touch ~/.claude/.groma-next-always` (on in every groma project), `rm ~/.claude/.groma-next-always` (off again), the reason (groma deliberately neither looks nor writes outside the project, so it does not know whether that file exists and does not create it), and that `next.hook: on` or `off` in `.groma/config.yaml` decides for this project alone, whatever the flag says. Never run these commands and never test for the file. A config that still holds `next.hook: off` from an older template: say that this line keeps the project off until it is removed or set to `auto`. `<project>/.claude/settings.local.json` or `<project>/.claude/settings.json` holds a Stop hook that runs `next-stop.sh` (from a run without the plugin): show that block in the findings report and suggest removing it, because the plugin ships the hook; until then the plugin's Stop hook steps aside, so the line still shows once.
   - **Yes, Stop hook, no plugin:** fill [templates/claude-stop-hook.json](templates/claude-stop-hook.json) with the absolute path of `../groma-methodology/scripts/next-stop.sh`. `<project>/.claude/settings.local.json` absent before this run: create it with one `hooks` object holding every hook accepted in steps 4 and 5. Present: put the `hooks` block into the findings report as a snippet. When groma created the file and `git check-ignore -q .claude/settings.local.json` fails, put the `.gitignore` line `.claude/settings.local.json` into the findings report and the summary: until it is ignored, `next.sh` counts the file as uncommitted work. Set `next.hook: on` in `.groma/config.yaml`; without it the hook follows the flag file `~/.claude/.groma-next-always` and prints nothing while that file is missing.
   - **Yes, status line:** never edit a status line setting or script, wherever it lives. Put into the findings report and the summary: the pill line (the last line of [templates/statusline-pill.sh](templates/statusline-pill.sh)) for a status line that already renders pills, and both forms of [templates/statusline-snippet.sh](templates/statusline-snippet.sh), the one line to add to an existing status line script and the standalone script with the `statusLine` setting that runs it. Resolve `{{next_script_absolute}}` to the absolute path of `../groma-methodology/scripts/next.sh`, and `{{next_script_pattern}}` to that path in double quotes; when the path runs through a plugin cache (`…/plugins/cache/<marketplace>/<plugin>/<version>/…`), write the version folder as `*` outside the quotes, as the template's comment shows, so that the line survives a plugin update.
   - **No:** change nothing; the AGENTS.md "Session end" line and `npx groma-cli next` remain. Plugin installed: say that the user's global flag `~/.claude/.groma-next-always`, when it exists, still switches the hooks on here, and offer to set `next.hook: off` in `.groma/config.yaml` to keep this project silent.
   - **Other agents:** offer a hook only for agents whose `hook.status` is `stable`. When the user asks for an `experimental` one, warn first: it is untested in that CLI's interactive mode and could behave differently there, up to starting another agent turn. After the user confirms, put its `event`, `config` and `format` with the `next-stop.sh` command into the findings report as a snippet (`stderr-exit2`: `next-stop.sh --stderr`); groma writes no hook file for these agents. `none`: no hook; the AGENTS.md line is the only mechanism.

6. **Report.** Files created, files left untouched with their snippet, hooks installed or declined, the flag command with its reason (plugin case), the status-line snippets.
