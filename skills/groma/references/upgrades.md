# Upgrade notes

Update mode reads this table to explain what a newer groma adds to a project that was initialized with an older version (`initialized_with` in `.groma/config.yaml`). Add a row with every release that changes mandatory docs, config schema or conventions.

| Version | Change | Action in update mode |
|---|---|---|
| 0.5.0 | Repository offer and first commit: `git-init.sh` and `first-commit.sh` (groma), stack table `references/gitignore.md`, config key `git.enabled` (default `true`), `npx groma-cli init --git init\|skip --commit yes\|no`, `docs-impact.sh` reports ADR candidates with a `note` outside git or before the first commit | In a repository: nothing new is asked. In a project without git whose config has no `git.enabled`: ask the repository question of the interview once; no records `git.enabled: false`, yes sets up the repository, and the first-commit question follows before the summary |
| 0.4.0 | OpenSpec 2.x: `next.sh` prints `/openspec-<step>-change` when the project has OpenSpec skills and no `opsx` command folder, `/opsx:<step>` while such a folder exists, and no command when neither exists; recipe key `generations` and touched path `.agents/skills/openspec-*` in `methodologies.yaml`; agent-neutral propose wording in the groma-agents methodology hint | Nothing to migrate: refreshed skill copies give the new commands. Existing `AGENTS.md` whose methodology hint names only `/opsx:propose` in a project with OpenSpec 2.x: put the new hint ("use the OpenSpec propose skill (`/openspec-propose`, or `/opsx:propose` with OpenSpec 1.x)") into the findings report as a snippet; an existing `AGENTS.md` is never edited (ADR 0006) |
| 0.4.0 | **Breaking, change names:** `<type><N>-<slug>` without zero padding (`c17-export`); a milestone is a section `## M<N>: <title>` in `docs/roadmap.md` with a release-gate checklist, not a change, and its changes are named `m<N>-<slug>`, `m<N>-spike-`, `m<N>-fix-`, `m<N>-refactor-<slug>`; the `d` type is gone from the defaults; `roadmap.sh` fills only the marker blocks `<!-- groma:changes m<N> -->` and no longer generates the file; `check-conventions.sh --suggest-migration`; `next-change-id.sh` prints ids without padding; `conventions.changes.digits` is ignored | Nothing is renamed, and `check-conventions.sh` stays green for old names (`INFO` lines, archived names ignored), so a CI check does not break. Follow "Migration" in groma-methodology's `references/conventions.md`: write every existing change name that is missing to `.groma/conventions-baseline.txt` (create or append), then put the output of `sh <groma-methodology>/scripts/check-conventions.sh --root <project> --suggest-migration` (new names, one roadmap section per old milestone change) into the findings report as snippets. Offer to remove `digits` from `conventions.changes`, and `d: docs` from its `types` when no active change is a `d` change (while the config lists it, `d` stays a type of that project). Existing `AGENTS.md` and `openspec/config.yaml`: put the new "Change naming" section of `templates/AGENTS.md` and the naming rule of `methodologies.yaml` into the findings report as snippets; neither file is edited (ADR 0006) |
| 0.4.0 | Skill copies without the CLI: `materialize.sh` (groma) copies and refreshes the groma skills in the project with the rules of `npx groma-cli init` and `update`; config key `steps.skills_copy`; `retired-skills.txt` (groma): copies of a skill are deleted only when it is listed there or the file left a shipped skill, never because a smaller or older groma lacks the skill; neither path replaces copies of a newer groma without `--allow-downgrade`; both treat symbolic links below a skills folder as conflicts and record written files before a run can be interrupted; `npx groma-cli update` makes no copies when `steps.skills_copy` is `skipped`; the copy is made also when the groma Claude plugin is installed (`groma init` default changed from skip to copy), with the command `claude plugin disable groma@groma --scope local` printed; `.groma/generated.json` keys in byte order | `steps.skills_copy` missing: when `.groma/generated.json` exists, run `sh scripts/materialize.sh --update <project>` and offer to add `skills_copy: done` to `steps`; otherwise ask the "Skill copies" question once. The first refresh may reorder the keys of `.groma/generated.json`; nothing else to migrate. Agents in `agents_via_plugin` stay without copies unless the user asks |
| 0.4.0 | Next-action hooks in the Claude Code plugin (`hooks/hooks.json`): SessionStart gives the next action to the agent (`next-session.sh`), Stop shows it; `next.hook` accepts `auto`, and a missing key now means `auto` (on exactly when `~/.claude/.groma-next-always` exists) instead of `off`; pill template `statusline-pill.sh` (groma-agents) | Config holds `next.hook: off` from the 0.3.0 template: say that this line keeps the project off whatever the global flag says, and offer to remove it. With the plugin: print the flag command and its reason as in groma-agents step 5; never create the flag file. Plugin installed and `<project>/.claude/settings.local.json` or `<project>/.claude/settings.json` holds a Stop hook that runs `next-stop.sh`: show that block and suggest removing it, because the plugin ships the hook (until then the plugin's Stop hook steps aside, so the line shows once); the user edits the file |
| 0.3.0 | Next action: `next.sh` and `next-stop.sh` (groma-methodology), config section `next` (`hook`, `reshow_minutes`), `hook` entries in `agents.yaml`, Stop hook and status-line templates (groma-agents), "Session end" section in the AGENTS.md template, `npx groma-cli next`, self-ignoring cache folder `.groma/.cache/` | Run groma-agents step 5 once (hook and status-line snippet; missing `next` keys mean `hook: auto`, `reshow_minutes: 30`). `AGENTS.md` that groma created and that has no "Session end" section: put the section of `templates/AGENTS.md` (with `{{next_script}}` resolved) into the findings report as a snippet; an existing `AGENTS.md` is never edited (ADR 0006) |
| 0.3.0 | Git workflow: config section `git` (`integrate`, `branch_per_change`, `commits`, `push`), `git-practice.sh` (groma-detect), strategies table `git-strategies.md` (groma-agents), "Git workflow" section in the AGENTS.md template, branch, commit, integrate and push steps in groma-loop, merge-base base in `docs-impact.sh` | Ask the two git questions of the interview (brownfield: with the `git-practice.sh` recommendation and its evidence) and offer to add the `git` section to the config; missing keys mean the defaults. Existing `AGENTS.md` without a "Git workflow" section: put the section of `templates/AGENTS.md` (placeholders resolved) into the findings report as a snippet; an existing `AGENTS.md` is never edited (ADR 0006), whoever wrote it |
| 0.3.0 | Code style: mandatory doc `docs/code-style.md`, `style-drift.sh` (groma-survey), tools table `code-style-tools.md` and config templates (groma-lay-out), "Code style" section in the AGENTS.md template, code-style line in the methodology context, style checks in groma-loop's tests gate and review prompt | Fill the code-style slot like any missing mandatory doc (brownfield: run the survey's Code style step first); report it as new in the findings. Do not create tool configs or ADRs unless the user asks for the style setup; existing `AGENTS.md`: put the "Code style" section of `templates/AGENTS.md` (with `{{style_checks}}` resolved) into the findings report as a snippet; existing `openspec/config.yaml`: print the context line from `methodologies.yaml` as a snippet |
| 0.2.0 | `npx groma-cli` CLI (init, update, status, doctor); config key `agents_via_plugin`; `.groma/generated.json` with hashes of copied skill files | Mention `npx groma-cli update` to refresh copies; nothing to migrate |
| 0.2.0 | Living docs: `docs-impact.sh` (groma-lay-out), config keys `docs.gate` and `docs.adr_from`, ADR frontmatter `origin`, docs reminders in `status.sh`, OpenSpec rules for docs impact, Docs task group and decision alternatives | Offer to add `docs.gate: review` and `docs.adr_from: design-alternatives` to the config (missing keys mean these defaults); existing `openspec/config.yaml`: print the three rules from `methodologies.yaml` as a snippet; existing `AGENTS.md`: put the "Living docs" bullet of `templates/AGENTS.md` (with `{{docs_impact_script}}` resolved) into the findings report as a snippet |
| 0.1.0 | Initial release: mandatory docs README, vision, concept, architecture, data-model, glossary, risks, adr/; config schema 1; change convention m/c/f/s/r/d (replaced in 0.4.0) | Create missing mandatory docs; nothing to migrate |
